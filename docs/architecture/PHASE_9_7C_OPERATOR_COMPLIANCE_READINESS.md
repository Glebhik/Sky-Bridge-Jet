# Phase 9.7.C — Operator compliance readiness center

Phase 9.7.C is based on merge `46b48d1e4c660ba4815977621ca607a2bf766472`. It depends only on the C0 `GET /api/v1/me/operator-compliance-readiness` projection and the A1 `GET /api/v1/me/operator-aircraft` collection. `/operator/compliance` performs exactly one of each read on initial active-organization load, manual refresh, and organization change; it never performs a per-aircraft compliance read.

The same-origin proxy adds only exact GET access to `me/operator-compliance-readiness`; the A1 aircraft GET was already intentionally exposed. Both typed clients send credentials, `cache: no-store`, an AbortSignal, and the validated active organization header. They contain no upstream origin, bearer token, or browser-supplied operator identifier. Generic admission, eligibility, evidence, document, platform review, payment, refund, webhook, and administration families remain closed.

All five operator roles receive the same read-only view. Multiple operator memberships require explicit selection before any request. Every request pair captures the organization ID and a monotonic epoch. Switching organizations aborts both reads, increments the epoch, clears both sections and errors, and discards any late response whose organization or epoch is stale, including A → B → A races.

The UI mirrors only C0 admission status, marketplace eligibility, safe blocker codes, and admission timestamps, plus the exact A1 aircraft projection. Null admission is reported as unavailable, not rejected. APPROVED is described only as marketplace admission. Eligibility copy is limited to current Sky Bridge Jet marketplace participation. Unknown future blocker codes fail closed to “Additional compliance requirement.” Aircraft cards state only the returned eligibility boolean and do not infer a reason.

Readiness and aircraft loading/errors are isolated. Errors never become negative compliance findings. Freshness is initial load, organization change, or an accessible manual Refresh; there is no polling, interval, socket, SSE, background watcher, or automatic mutation. The page explains that the server revalidates Offer commands and that readiness does not guarantee availability, crew, permits, slots, customer acceptance, or Booking confirmation.

There is no evidence list, upload, submission, document vault, review, approval, rejection, or suspension UI. Browser types and DOM exclude raw evidence, storage references, review notes or identities, audit metadata, internal operator identity, foreign tenant data, customer/passenger data, and payment/provider data. Copy does not claim certification, regulatory approval, airworthiness, or authorization to fly.

The responsive layout is single-column through tablet and a balanced two-column readiness/aircraft layout on desktop, with semantic sections, headings, lists, definition lists, textual status, visible focus, and non-color-only outcomes. Backend inventory remains 93 registered / 89 OpenAPI / 4 documentation routes. Alembic remains `20260827_0010`; Phase 9.7.C adds no API production code, migration, dependency, lockfile, or environment change. Platform review, evidence workflows, aircraft management, and broader compliance operations remain deferred.
